# Software Engineer workflow clarity delta

## Goal

Make the Implementation phase understandable to a first-time user: explain when code is written, what the seven evidence artifacts mean, and turn engineering approval failures into ordered recovery actions. Preserve the evidence gate while allowing legacy Runs to use approved User Story acceptance criteria when no structured Change Contract exists.

## Preserved behaviour

The fixed six-phase workflow, seven registered engineering artifacts, human approval boundary, upstream Product/Design/Architecture clearances, independent verification requirements, and semantic approval gate remain unchanged.

## ADDED

- A four-step Implementation guide shown in the phase and execution UI.
- Plain-language timing, purpose, and reviewer responsibility for every engineering artifact.
- Structured Web guidance for engineering-evidence approval failures, with artifact-specific recovery actions and retained technical details.
- A legacy acceptance-criteria resolver that reads stable AC IDs from the approved User Stories selected for the completed implementation execution.
- An implementation preflight that rejects explicitly blocked Product, Design, or Architecture inputs before creating a Codex execution.
- A recommended review order that opens the implementation summary first, puts the three human-facing documents first, and labels the remaining four as audit detail.
- A structured cross-phase human-decision summary derived from active Product, Design, and Architecture artifacts.
- A decision-capture action that records bounded, auditable answers in the existing review history and immediately routes the current role to update its formal artifacts.

## MODIFIED

- The Software Engineer execution action explicitly says that this is the moment Codex writes code, runs checks, and generates evidence.
- Implementation input and output selection is automatic in the normal path: approved upstream evidence becomes one read-only input bundle and the seven outputs become one engineering evidence pack. Per-artifact rerun remains available from review.
- Product, Design, and Architecture approval is fail-closed when their active handoff still contains an explicit blocker or unresolved human decision.
- The workflow board distinguishes an internally blocked approved legacy phase as an inconsistency instead of presenting it as healthy approval.
- Legacy implementation approval uses structured Change Contract criteria first, then approved selected User Story criteria; it never derives authority from engineering-authored evidence.

## REMOVED

None.

## REMOVED audit

The artifact registry, phase order, role ownership, validator checks, and all seven artifact IDs were compared before this change. No evidence artifact or approval requirement is removed or bypassed.

## Risk note

Loose Markdown parsing could accidentally treat arbitrary text as an acceptance criterion. The fallback therefore accepts only stable AC headings inside the approved `user-stories` artifact selected for the implementation execution, deduplicates IDs, and still fails closed when none exist.

## Acceptance criteria

- **AC-CLARITY-001:** The Implementation phase visibly explains the four steps: confirm ACs, start implementation/write code, review grouped evidence, and approve to unlock Tester.
- **AC-CLARITY-002:** All seven engineering artifacts have plain-language timing, purpose, and a concrete “what the human checks” description.
- **AC-CLARITY-003:** The primary Software Engineer action makes clear that clicking it starts real code/test work; evidence documents are generated by Codex rather than pre-filled by the user.
- **AC-CLARITY-004:** `ENGINEERING_EVIDENCE_GATE_FAILED` is rendered as deduplicated Chinese recovery actions while preserving raw diagnostics.
- **AC-CLARITY-005:** The three reported failures map respectively to: repair upstream AC authority, resolve/re-run a blocked implementation, and resolve or replace `<...>`, `{{...}}`, `TBD`, or `TODO` content in the plan.
- **AC-CLARITY-006:** A legacy Run with no structured Change Contract can approve against stable acceptance criteria extracted from its approved, selected User Stories.
- **AC-CLARITY-007:** A legacy Run with neither structured criteria nor stable User Story AC headings remains blocked; no objective or engineering document is promoted to authoritative criteria.
- **AC-CLARITY-008:** Root and platform typecheck, tests, and build pass without changing the six-phase model or artifact registry.
- **AC-CLARITY-009:** Implementation with an explicitly blocked PRD, Design status/blocker list, or Architecture status is rejected before `createExecution`; no “writing code” state or Markdown rerun begins.
- **AC-CLARITY-010:** The normal Implementation dialog has no actionable upstream/output checkboxes: it automatically uses approved inputs and generates the full seven-artifact pack; review retains explicit per-artifact rerun.
- **AC-CLARITY-011:** The Implementation action says “检查条件并开始写代码”; `IMPLEMENTATION_NOT_READY` renders role-owned blockers and next actions rather than a generic execution failure.
- **AC-CLARITY-012:** Once an execution reaches `running`, the UI may truthfully say code/test work is in progress because the readiness preflight has already passed.
- **AC-CLARITY-013:** Implementation review defaults to implementation notes, recommends notes → independent tests → seven-lens review, and explains that the remaining four records are audit detail still checked automatically.
- **AC-CLARITY-014:** The Run API exposes one structured decision summary for Product, Design, and Architecture, including item ID, owner, kind, source artifact, next action, captured response, and whether an approved phase is internally inconsistent.
- **AC-CLARITY-015:** Product approval rejects explicit pending-human/not-ready status, unchecked human questions, or unresolved Needs-decision/TBD fields; Design approval requires `ready-for-engineering`, no blockers, and no open questions; Architecture approval rejects non-acceptance open decisions in addition to its existing selection/rulebook gate.
- **AC-CLARITY-016:** The Web shows a cross-phase decision dashboard and per-phase decision box before approval, separates human decisions from role-owned work and upstream dependencies, and disables approval while blocking items remain.
- **AC-CLARITY-017:** A human can submit structured responses from a ready, awaiting-review, or inconsistent-approved upstream phase. The platform records a request-changes review with a machine-readable decision block, invalidates downstream phases, then opens the current role's rerun flow so the answer must be materialized into formal artifacts. When a downstream phase becomes Ready with stale role work or old upstream dependencies, its action runs that role directly instead of asking the human to repeat the upstream decision.
- **AC-CLARITY-018:** An approved legacy phase whose active artifact still contains blockers is labeled as an inconsistency with a recovery action; it is not counted as clean progress in the decision UI.
- **AC-CLARITY-019:** The fixed six-phase order, role owners, existing artifact registry, and database schema remain unchanged.
