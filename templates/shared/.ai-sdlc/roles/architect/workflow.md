# Architect workflow

Turn confirmed product and design intent into divergent options and a decision-ready architecture pack.

The recorded Architecture disposition is authoritative. `skip` and `reuse` are platform actions and must not invoke this workflow. Under `partial`, modify only the declared affected outputs and preserve inherited checkpoint evidence. Under `full`, follow the complete steps below.

## Steps

1. Read `ai-native.yaml`, `.ai-sdlc/workflows/default.md`, the immutable Change Contract, the active Product and Design clearances, `.ai-sdlc/roles/architect/config.yaml`, every applicable configured input, and the existing architecture pack. A valid Design `skip` clearance replaces a placeholder design spec; Product `direct` likewise replaces fake PRD/story inputs. When a ready design spec contains `deferred_validations`, carry their measurable targets into NFR and test guidance as Tester-owned Verification obligations; do not relabel them as open Design decisions or Architecture blockers.
2. Resolve every input and output through the global artifact registry and the artifact owner's role config. Do not hardcode `docs` or the default Architect directory.
3. Read the [rulebook index](references/architecture-rules.md), its always-loaded [core rules](references/rules/core.md), and the active execution contract. Run `node .ai-sdlc/roles/architect/scripts/rulebook-digest.mjs` and use its exact output as `catalogDigest` in every rulebook v1 block; this digest also binds the configured `rulebook.project_mode`. Read the current Discovery and Options revisions even when they are not selected for update. If their digest differs from the current rulebook or configured mode, the old checkpoint and selection are stale; block selected-state work and request a checkpoint rerun. Separate confirmed facts, measured evidence, assumptions, recommendations, and human decisions.
4. If `architecture-discovery-context` is selected, classify the affected scope as Greenfield, Brownfield, or Hybrid from evidence unless a human sets `rulebook.project_mode` to one of those modes instead of `auto`; evaluate all six conditional pack routes; load only packs marked Applicable or Blocked by material uncertainty; then create or update the four-layer context, complete all six Rule Pack Applicability rows, and replace every placeholder in its unique rulebook v1 JSON machine block. If Discovery is not selected, treat its reviewed revision as read-only and verify it still covers the current evidence. Never silently omit a pack or apply Greenfield defaults to evidenced Brownfield scope.
5. If `architecture-options` is selected, create or update at least `quality.minimum_options` genuinely different options, score them against evidence-backed criteria, identify rule conflicts or exceptions per option, and make a provisional recommendation. Every option heading is the exact canonical form `## Option <ID>: <name>`; this is a machine contract, not a styling choice. Its rulebook v1 JSON block must enumerate every rule from every Applicable pack exactly once. If Options is not selected, treat its reviewed revision as read-only. A rule may constrain or reject an option but must not silently select it. If new evidence or the selected option would change project mode, pack applicability, a load-bearing option, or its rule constraints while Discovery or Options is read-only, do not edit an unselected artifact: mark the active selected outputs Blocked and ask the human to rerun the affected bootstrap outputs, review them, and record a new option selection against their new revisions.
   When review feedback contains a captured human decision such as `ARCH-OBS-002`, copy the decision into the Rule Constraints, machine block, NFR/searchable signal, redaction, ownership, and verification evidence required by that rule. Remove the matching unchecked decision only when those formal fields are complete, and do not ask for the same answer again. A `MUST` rule whose catalog deviation is `N/A` cannot be converted into a policy exception by prose.
6. Create or update the resolved `architecture` artifact from `.ai-sdlc/templates/architecture.md`. Link the context and options as active, summarize all six rule-pack statuses, mark every selected-state artifact as pending, and keep its unique rulebook v1 JSON block consistent with Discovery. Use machine state `awaiting_selection` until selection and `ready_for_human_acceptance` only after all selected-state evidence is complete.
7. Before asking for option selection, make every concrete rule/dependency blocker decision-ready under `## Open Human Decisions` using a stable ID and plain-language choices; never emit only “close gaps”. Do not ask the human to select an option while its machine rule row remains `blocked`. Once concrete blockers are resolved, Check for human selection evidence. In a platform-managed run, it is a review-feedback line `Selected option: <ID>` that names one option in the current options revision. If evidence is absent, materialize the awaiting-selection scaffolds below for every selected output in the active execution contract, set the index to `Awaiting human selection`, and only then stop selected-state work. If it is present, verify that it selects exactly one documented option before continuing.
8. Create the C4 context and container views from the `.mmd` templates. Copy the exact platform-verified selection evidence into each template's one-line `ai-sdlc:architecture-selection:v1` marker, add only evidence-backed elements, and render-check both files in the project's actual Mermaid runtime.
9. Record each major decision as a proposed ADR from `.ai-sdlc/templates/architecture-adr.md`. Put it in the resolved `architecture-adrs` directory as `ADR-<three-digits>-<kebab-case-title>.md`. Add one non-ADR `00-selection.md` containing the exact Markdown `ai-sdlc:architecture-selection:v1` marker for this selected-state revision. Preserve existing IDs and include related rule IDs and Discovery scope IDs, rejected alternatives, consequences, and a short agent-readable summary with explicit `Must` and `Do not` rules. A `DEFAULT` whose catalog says `ADR required` needs an ADR to deviate; a `MUST` or `FORBIDDEN` conflict stays blocked until a human approves a superseding decision or changes the rule.
10. Record only patterns that were considered. Place each adopted pattern on a named C4 L2 element and state its rule IDs and trade-off. In the Rule Disposition Register and its unique rulebook v1 JSON block, enumerate every rule × affected scope from every Applicable pack exactly once; link its scope, C4, ADR, Pattern, NFR, test, contrary trigger evidence, justified deviation, approved exception, or blocker. Human-facing `Adopted` maps to machine state `satisfied`; the other machine states are `not_triggered`, `justified_deviation`, `exception`, and `blocked`. `justified_deviation` is allowed only when the rule is `DEFAULT` and its catalog `Deviation` policy is `Reason allowed`; `ADR required` can never use it. An exception or Brownfield migration decision must reference a human-revised accepted ADR that names the rule, affected scope, and effect.
11. Create at least `quality.minimum_nfrs` measurable NFR budgets across at least `quality.minimum_nfr_families` relevant families from `.ai-sdlc/templates/architecture-nfrs.md`. Copy the exact selection marker, then give each complete budget source rule IDs where applicable, a target, measurement window, responsible container, test method, evidence, and a failure signal. If the configured floor does not fit the project, block and ask a human to change it; never add irrelevant NFRs to reach a number.
12. Ask a fresh session or independent reviewer to run the three-stressor premortem from `.ai-sdlc/templates/architecture-adversarial.md`. Copy the exact selection marker. If independence cannot be shown, mark the review as pending.
13. Refresh the index with current links, status, freshness, rule-pack conformance, ADR applicability, and open decisions.
14. Run the completion checks below and return unresolved decisions to the human owner.

## Awaiting-selection scaffolds

A pause is a pack status, not permission to omit a contracted output. Before returning without human option-selection evidence, every output selected by the active execution contract must exist and contain non-whitespace content. If no output subset is supplied, treat every Architect phase output as selected. Never touch an unselected registered output.

- Complete selected `architecture`, `architecture-discovery-context`, and `architecture-options` artifacts normally, using only available evidence.
- For each selected C4 `.mmd` artifact, write a valid Mermaid flowchart that contains only a Pending notice and the required human next action. Do not depict systems, containers, relationships, technologies, or a selected option.
- For the selected `architecture-adrs` directory, create a non-empty `README.md` that states why decisions are pending, who must select an option, and what happens next. State explicitly that the file is not an ADR; do not allocate a fake ADR number.
- For each selected pattern, NFR, or adversarial Markdown artifact, write a short Pending document with the blocker, human owner, evidence needed, and next action. Do not fill template fields with guesses.
- Link every scaffold from the selected `architecture` index and mark it Pending. A scaffold never makes selected-state work active and never satisfies the architecture completion gate.

After valid human selection evidence exists, replace the relevant scaffolds with evidence-backed content and continue from step 8.

Discovery and Options are reviewed checkpoint artifacts. A normal selected-state run reads them but does not rewrite them. Any evidence change that invalidates either artifact also invalidates the old selection; selected-state work stays Blocked until the human reruns the affected bootstrap artifact(s) and selects again.

## Completion checks

- Every output selected by the active execution contract exists and is non-empty, including a directory artifact with at least one non-empty regular file.
- No registered output outside the active execution contract was modified. In selected-state work, Discovery and Options remain byte-for-byte unchanged unless explicitly selected for rerun.
- When `rulebook.validation` is `required`, Discovery, Options, Architecture, and selected-state Patterns each contain exactly one valid `ai-sdlc:architecture-rulebook:v1` JSON block with no placeholders or unknown fields.
- Every machine block uses the exact current digest from `rulebook-digest.mjs`. A rulebook change after selection requires refreshed checkpoint artifacts and a new human selection.
- Architecture, Patterns, both C4 views, the ADR directory marker, NFRs, and the premortem all bind the exact same platform selection evidence. The marker prevents stale or cross-selection material; it does not replace human review of semantic alignment.
- The platform semantic gate accepts option selection only when the checkpoint blocks contain all six packs and the exact Applicable rule set; it accepts final approval only when every applicable rule × affected scope has one non-blocked disposition and every cross-artifact status agrees.
- Options exist before any selected-state C4 diagram.
- Human selection evidence is recorded before C4, ADR, or pattern choices are treated as active.
- Discovery classifies project mode with evidence and classifies all six conditional rule packs as Applicable, Not applicable, or Blocked.
- Every rule in every Applicable pack affects an option or is explicitly shown as not constraining it; no rule silently preselects the option.
- After valid human selection, every rule × affected scope from every Applicable pack appears exactly once in the Rule Disposition Register with evidence, a justified deviation, an exception, or a blocker.
- A Brownfield or existing Hybrid boundary is not migrated to a Greenfield default without an accepted migration ADR.
- Any unresolved applicable `MUST`, triggered `WHEN`, `FORBIDDEN`, or material `DEFAULT` exception keeps the pack from `Ready for human acceptance`.
- C4 L1 shows the focal system and every evidenced person or external system, without container detail.
- C4 L2 shows every evidenced executable or deployable container, data owner, high-level technology, and communication path.
- Every active ADR has consequences and agent-readable `Must` and `Do not` rules.
- Every ADR appears once in the architecture index, and no existing ADR ID was reused or renumbered.
- Every active pattern has a C4 L2 location, a reason, and a trade-off.
- The NFR set reaches both configured minimums, or the pack records a human-approved config change.
- No approved NFR is missing a numeric or binary target, a window, or a test method.
- The adversarial review covers load, malicious input, and external dependency failure, with at least the configured findings per stressor.
- The index clearly separates accepted, proposed, blocked, and pending material.
- Human acceptance and its evidence are recorded before the architecture phase is complete.

Keep the index at `Ready for human acceptance` until a human accepts it. Do not fill the acceptance fields yourself or claim the pack is complete when a human decision, measurable target, render check, or independent review is missing.
